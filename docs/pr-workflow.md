# PR Workflow Guide

Эта схема подходит для сдачи инкрементов на Практикуме.

## Главное правило

- `main` должен содержать только код, который уже принят ментором
- каждый новый инкремент делается в отдельной ветке `iterN`
- PR всегда открывается из `iterN` в `main`

## Базовый цикл работы

1. Переключиться на `main`
2. Обновить `main`
3. Создать новую ветку `iterN` от `main`
4. Сделать изменения
5. Запушить ветку
6. Открыть PR `iterN -> main`
7. Дождаться автотестов и ревью ментора
8. После принятия смёржить PR в `main`
9. Для следующего инкремента снова создать новую ветку от свежего `main`

## Схема веток

```text
main
  |
  o--- iter1 -------- PR #1 --------> main
               merge after mentor approval
  |
  o--- iter2 -------- PR #2 --------> main
               merge after mentor approval
  |
  o--- iter3 -------- PR #3 --------> main
```

## Как делать правильно

Для `iter1`:

```bash
git checkout main
git pull
git checkout -b iter1
```

После завершения работы:

```bash
git add .
git commit -m "Implement iter1"
git push -u origin iter1
```

Потом открыть PR:

```text
iter1 -> main
```

После принятия ментором:

```bash
git checkout main
git pull
```

И только потом начинать `iter2`:

```bash
git checkout -b iter2
```

## Как делать `iter2` и `iter3`

Каждый следующий инкремент создается от актуального `main`, а не от предыдущей `iter`-ветки.

Правильная последовательность:

```text
main -> iter1 -> merge to main
main -> iter2 -> merge to main
main -> iter3 -> merge to main
```

## Почему не стоит делать новую ветку от предыдущей `iter`

Плохой сценарий:

```text
main
  \
   iter1
      \
       iter2
          \
           iter3
```

Проблемы:

- PR `iter2 -> main` включает изменения из `iter1`
- PR `iter3 -> main` включает изменения и из `iter1`, и из `iter2`
- после замечаний ментора в одной ветке приходится чинить цепочку зависимых веток
- diff становится шумным и плохо читается

## Частая ошибка

Частая ошибка выглядит так:

```text
main -> iter1 -> iter2 -> iter3 -> iter4
```

То есть каждая новая ветка создается не от `main`, а от предыдущей `iter`.

В результате:

- история становится цепочкой зависимых веток
- PR перестают показывать только текущий инкремент
- исправления в ранней ветке влияют на все следующие

Если замечаешь у себя такую схему, лучше как можно раньше вернуться к модели:

```text
main -> iterN
main -> iterN+1
main -> iterN+2
```

## Если уже создал ветку от предыдущей `iter`

Это не катастрофа, но потом лучше перенести ветку на свежий `main`.

Пример:

```text
main -> iter1
iter1 -> iter2
```

После мержа `iter1` в `main`:

```bash
git checkout iter2
git rebase main
```

После этого ветка `iter2` будет основана уже на актуальном `main`.

## Когда вливать ветку в `main`

Вливать ветку в `main` нужно после того, как:

- PR проверен автотестами
- ментор принял работу

Смысл такой:

- `main` остается чистой принятой базой
- новый инкремент всегда начинается от проверенного состояния

## Почему тесты работают и в `iterN`, и в `main`

Автотесты Практикума завязаны не только на ветки `iterN`, но и на `main`.

Логика такая:

- в `iter1` запускаются тесты для первого инкремента
- в `iter2` запускаются тесты для первого и второго инкремента
- в `iter3` запускаются тесты для первых трех инкрементов
- в `main` запускаются тесты для всех уже реализованных инкрементов

Смысл в том, что:

- ветка `iterN` проверяет текущую сдаваемую работу
- ветка `main` хранит накопленное рабочее состояние проекта

Поэтому merge в `main` не ломает процесс, а является его частью:

- сначала ты сдаешь инкремент в `iterN`
- после принятия ментором вливаешь его в `main`
- следующий инкремент начинаешь уже от `main`

Именно поэтому к моменту сдачи поздних инкрементов должны проходить и предыдущие тоже.

## Что делать, если ментор попросил правки

Ничего заново создавать не нужно.

Нужно:

1. Внести правки в ту же ветку `iterN`
2. Закоммитить изменения
3. Запушить их в ту же ветку

PR обновится автоматически.

## Короткая рабочая памятка

```bash
git checkout main
git pull
git checkout -b iterN
```

После работы:

```bash
git add .
git commit -m "Implement iterN"
git push -u origin iterN
```

После принятия:

```bash
git checkout main
git pull
git checkout -b iterN+1
```
